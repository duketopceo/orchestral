# Plan: interactive TUI (`harness.py tui`)

Replaces the one-shot rich table (`orchestral/tui.py`, 0% covered) with a
Textual app. `textual` ships as an optional extra `[tui]` (like `[shots]`)
so the pinned base stack is unchanged; `run_tui` lazy-imports and prints
an install hint when missing.

## Architecture

```
orchestral/tui/
  __init__.py    run_tui() entry + lazy textual import
  state.py       pure domain — JobStatus lifecycle enum, Job, RunFilter,
                 formatters. No textual imports; unit-tested directly.
  app.py         OrchestralApp — composition root, key bindings,
                 thread workers for DB loads and run launches
  screens.py     RunDetailScreen, GroupsScreen, HelpScreen, LaunchScreen
  widgets.py     StatusBar (run counts + active jobs + hints)
```

Domain rules the views never own: run filtering, job lifecycle
transitions (`queued -> running -> succeeded/failed/cancelled`),
aggregate math (delegated to `orchestral.stats.aggregate`), DB access
(`RunStore` behind a loader function). Views render state and dispatch
actions only.

## Screens / flows

- **Runs (main):** DataTable — id, group, rep, task, orch, worker, cost,
  score, pass, status, started. `/` filters (substring over id/task/
  orch/worker/group/status). `r` refreshes. Auto-refresh every 5s while
  any job is running.
- **Run detail** (`Enter` on a row): summary header (status, cost,
  tokens, score, failure reason, group/rep, dir), calls table from
  `index.db`, tabs for events / metrics / report / plan.
- **Groups** (`g`): replicate-cell aggregate table from `stats.aggregate`.
- **Launch** (`n`, modal): task select, orchestrator select, worker
  select, replicates, seed, dry-run checkbox. Runs on a thread worker;
  job shows in the status bar; runs appear in the table on refresh.
- **Help** (`?`, modal): full key map.
- Keys: `j/k`/arrows navigate, `Enter` open, `Esc` back/close modal,
  `x` cancel running job, `q` quit (only when no input focused).

## Runner change

`Runner(cancel_event=threading.Event)` — checked before planning and at
the top of each subtask iteration. On set: raise `RunCancelled`, mark the
run `status="cancelled"`, `failure_reason="cancelled"`, log
`run_cancelled`, write `metrics.json`, return meta (no re-raise — cancel
is a normal outcome, not an error).

## Testing

- `state.py` unit tests: filter matching, lifecycle transitions,
  illegal-transition rejection, formatters.
- Textual `run_test()` pilot tests (`IsolatedAsyncioTestCase`): app
  mounts with seeded runs, `/` filters, `Enter` pushes detail, `g`/`?`
  open their screens, launch modal submits a dry-run job that reaches
  SUCCEEDED and lands a row, `x` cancels, `q` quits.
- Runner: `cancel_event` pre-set → run records `cancelled` and returns.

## Risks

- Textual is the first new runtime dep; contained to the `[tui]` extra
  and the `tui/` package. AGENTS.md stack note updated to say so.
- `RunDetailScreen` reads run-dir files; malformed JSONL/JSON must not
  crash the screen — per-file parse guarded.
