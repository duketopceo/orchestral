## Interpretation

- The honest dead pool is small relative to code size — expect the report
  (U3) to land tens of candidates, not hundreds. The bigger prize is likely
  Tier-B/C simplification-adjacent code, deferred by plan scope.
- `state.py` (3,349 LOC) has only 1 zero-inbound function — its size is
  breadth, not dead weight. Sweep sizing should follow the report, not LOC.
- Test volume (38k LOC) means test-helper dead code is plausible; R5 rules
  apply — delete test code only with the dead code it covered.

## Reproduce

Index: `index_repository` on repo root, `mode=full`, `persistence=true`.
Zero-inbound query: `MATCH (n:Function) WHERE n.in_degree = 0 RETURN
n.file_path, count(n) ORDER BY count(n) DESC` via `query_graph`. LOC: `wc -l` per dir.
Next census after the U4 sweeps complete; the delta is the program score.

## U3 report — tiered candidates (2026-10-09)

`docs/analysis/dead-code-report-2026-10.json`, generated by
`scripts/dead_code_report.py` over graph.db.zst @ HEAD + vulture
(min-confidence 60) + instrumented-suite coverage (2424 tests).

- **Canonical pool reconciliation:** the census's 94 used `in_degree`
  (CALL_REFERENCE/INHERITS folded in). Zero-inbound over `CALLS|USAGE`
  only — the canonical query — yields ~2,850 raw nodes, dominated by
  unittest-discovery names in `tests/` (2,481 pattern exclusions) and
  71 registry minus-list hits. After those subtractions and dropping
  51 coverage-executed candidates, the residual pool is **5 python B
  rows, 227 tests-surface B rows, 16 JS C rows — 0 Tier A**.
- The honest read: the repo carries no confidently-deletable dead code.
  Every survivor is dispatch-shadowed (framework callback names,
  interface stubs redefined with callers, lazy-imported modules,
  `__getattr__` proxies) or test code that rides with its subject.
  Coverage was the decisive third source: `summarize_unittest_output`,
  vulture-flagged and graph-dead, turned out test-executed.
- U4 deletion sweeps therefore have no batch to run; the 4f-tier
  simplification work should target the 227 tests-surface rows and the
  JS C rows only as ride-alongs, never as stand-alone deletions.
